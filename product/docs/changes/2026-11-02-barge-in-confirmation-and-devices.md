# 先确认再打断、认耳机、设备切换

日期：2026-11-02。依据两次真机测试：202611022028 戴 AirPods，202611022032 外放。

## 测到的问题

1. **没认出 AirPods**：`headset` 一直是 0。iPhone Safari 给出的麦克风名字里不带 AirPods，所以按名字判断的办法没用。戴耳机时，打断监听仍然在两种麦克风之间来回切换，打断之后又出现了纯静音的麦克风（第 13、14 轮）。
2. **狗叫被当成说话**：判断开口只看音量和持续时间，狗叫同样会触发。第 4 轮的声音高出判断线 22 倍。
3. **摘耳机后很混乱**：声音忽大忽小、耳机或手机里突然一声很响的爆音、小宇的声音消失。原因是 iPhone 在对话中途切换声音设备，页面原来既没有处理，也没有记录。

## 做法

**记录**（测试数据里只有数字）：
- `inputKind`：麦克风名字属于哪一类。0 是没有名字，1 是手机自带，2 是耳机，3 是其他。不保存名字本身，因为里面可能带人名，比如"某某的 AirPods"。
- `inputs`：有几个麦克风可选。
- `audio-device-change`：声音设备发生了切换，同时记下当时的麦克风数量。
- `playback-state`：播放被系统中断，比如来电、Siri 或设备切换，记下当时的状态。

**认耳机**：名字显示是耳机，或者可选麦克风有两个以上、而当前用的又不是手机自带的，就算戴着耳机。

**先确认再打断**：
- 检测到声音时，小宇的音量降到 20%，同时开始听。这时她并没有停下。
- 识别服务一听出第一个字，服务器就只给页面发一个 `heard` 信号，不带任何文字。页面收到后才真正停下小宇，并按已播记录标记她说到了哪里。这一步会记作 `barge-in-confirmed`。
- 如果什么字都没识别出来（比如狗叫、关门声），就恢复音量，继续监听打断。这一步会记作 `barge-in-dismissed`。
- 如果小宇的声音没有经过页面的播放通道，就和以前一样立刻停下。用批量识别时没有 `heard` 信号，等整句识别出文字再确认。
- 实测识别服务在开口后约 0.4–0.5 秒发回第一个字。但识别连接要 1.1–2.4 秒才建立，所以从检测到声音到确认，可能要 1.5–2.5 秒。这段时间小宇是小声说着的。

**设备切换时**：
- 先把小宇的声音静音，0.3 秒后再慢慢恢复，避免切换时的爆音。
- 关掉当前的打断麦克风，它可能已经是错的那个了。
- 清空回声消除学到的扬声器情况，重新认耳机。
- 如果播放被中断，就恢复播放。

## 测试

- `tests/streaming-reply.test.mjs`：
  - 检测到声音时只降低音量，识别出第一个字后才停下，并带上已听到的部分；
  - 狗叫时恢复音量，重新监听；
  - 声音不能降低时立刻停下。
- `tests/realtime-asr.test.mjs`：`heard` 信号只发一次，不带文字，空的中间结果不算。
- `tests/barge-in-browser.mjs`（Chromium）：
  - 声音触发后小宇没停，什么都没识别出来时恢复，并重新监听；
  - 识别出说话后确认打断，下一轮请求里带上已听到的部分；
  - 模拟 AirPods 时记录 `inputKind: 2`；
  - 设备切换会被记录，测试数据里不出现设备名。
- `npm run check` 和 17 个关键浏览器流程全部通过。

## 未验证

- iPhone 上用 AirPods 时，`inputs` 是不是真的会多出一个，要看下一次导出的数据。
- 确认之前那段小声说话，用外放时是否又会出现通话音质。原因是这期间听孩子说话的麦克风是正常处理的，iOS 可能会切到通话模式。
- 爆音是否消失。
