# B：未发布候选与正式历史分离

日期：2026-10-28。承接 A 的运行身份/诊断，本轮只改变普通文本对话候选的存放与接收；保留现有绘图、本地保护回应、语音模式、UI 等待状态和存储机制。

## 解决的问题

此前 pending 提交把本地备用回复和孩子原话一起写入 messages，再由 quick 覆盖备用回复。虽然停止时有清理，但等待期间保存、导出或读取历史仍可能看见一个尚未接受的回答。把“最后一条老师回复”当作候选，也不适合候选迁出后的历史结构。

现在 pending 只提交本轮孩子原话及既有受限域变更；候选保留在 conversationController 当前 run 调用的局部数据中，不进入 appStore、正式 messages 或 A 的公开诊断。没有新增全局候选库、事件总线或第二份可写历史。网络已取消但还未结束时，旧调用仍可能短暂持有局部引用；不宣称取消立即释放全部内存。

## 当前合同

| 阶段 | 正式历史 | 接收与副作用 |
|---|---|---|
| pending | 旧历史 + 本轮孩子原话，无本轮 tutor 占位 | 保留原受限域合并；不增加回合数、不新建成长片段 |
| quick 返回，尚未接受 | 不变 | 安全检查和身份检查通过后准备提交；返回本身不构成发布 |
| quick 接受 | 在对应孩子原话之后插入一条带 turnId 的回复 | 核对会话、原话内容、当前状态及回复身份仍未被占用；只计数一次，沿用原保存/播报入口 |
| complete | 不改已接受的消息 | 后台补全仍只合并受限证据/状态，沿用冲突保护 |
| protected | 沿用原安全回应与本轮原话过滤规则 | 不把不安全输出作为正式回复；不是普通 quick 插入 |
| cancel / 新回合 | 保留已有孩子原话、已接受回复 | 清除等待标记；回合代次使旧结果失效，不再按最后一条 tutor 猜测并删除消息 |

quick 提交由“改写已有候选文本”改为“插入指定回复”。完整提交必须已有目标回复；quick/protected 必须尚无目标回复。即使回答文字与旧历史相同，重复提交也不会新增第二条或重复计数。消息内容修改、会话变化、阶段变化及晚到结果仍被拒收。若同时出现其他消息，新回复放在自己的孩子原话之后，不覆盖后来消息。

局部备用回答仍作为既有 fallbackReply 参数交给文本适配器，这不是聊天历史；本轮没有取消网络失败时的备用回答策略。被正式接收的备用回答属于已接受回复，可以保存。B 的保证是未接受候选不出现在正式历史或由该历史派生的模型上下文/导出/成长片段，而非所有请求中完全没有备用文本。

“接受”继续表示内存业务提交被接收，不等于已经成功持久化、已经播音或孩子已经听完。保存失败及实际已播语义未在本轮收敛。

## 页面重开与旧数据

新增 recoverInterruptedConversationState，仅在页面加载现有状态时调用：

- 对无法恢复的 pending/enrichmentPending 清除等待标记，不自动重新请求或播报。
- 旧版本 quick-reply 待定状态中，只有末尾紧邻的 child/tutor 对具有相同 turnId 和对应 ID，才移除可辨认的旧候选；保留孩子原话和更早的已接受回答。
- 新版本等待状态本来没有候选；后台补全时已有的回复保留。
- 没有足够身份信息的旧消息不猜测删除；不宣称清洗了全部历史、旧成长片段或外部备份。

恢复函数不原地修改输入；页面初始化仍会通过原保存入口保存处理后的当前状态。原导出文件不改动。经备份界面恢复时，既有 parseArchiveBackup 本来就只恢复档案并重置当前会话；本轮不改此策略、备份格式或跨记录事务。

## 修改范围

- conversationCommit：pending 只携带 child；quick 携带受限回复对象，接收时检查身份并插入；complete 仍要求目标回复存在。
- conversationController：把候选留在当前调用内；等待时以“回复尚不存在”作为检查条件，接受后检查已接受的回复内容。
- conversationState：构造待接收回复的插入结果；取消只清等待标记，另设页面加载的旧候选兼容处理。
- app：仅接入页面加载处理。未搬动保存/播报、成长写入或绘图编排。
- 测试：调整原候选占位契约断言，保留原并发/拒收目的；加强停止前的检查，新增正常候选生命周期与恢复浏览器流程。
