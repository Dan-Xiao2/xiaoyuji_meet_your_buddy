# TTS 首帧慢：根因与连接预热

> 2026-11-01 后续：预热方案已调整为“30 秒长连接 + 只在开口时预热”，Agent 在最终转写时、正式页面在说完时的预热已去掉（会抢占回答请求的连接）。见 [模型首句延迟](2026-11-01-llm-first-sentence.md)。

日期：2026-11-01。前置：[延迟拆分](2026-11-01-latency-breakdown.md)中 TTS 请求到首帧平均 1394ms，明显慢于 10 月独立探测的 677ms。

## 结论

**慢在冷连接，不在供应商合成，也不在本地分帧。** Node 内置 fetch 只让空闲的 keep-alive 连接保留约 4 秒。语音对话里，孩子说话加上模型思考的时间远超 4 秒，所以每轮回答的第一句 TTS 都要重新做 TCP+TLS 握手。本机到北京端点的往返约 170–290ms，TLS 完成约 0.35–0.58s，首个请求还会多出连接建立和进程首调用的开销。

修复方式：孩子开始说话、ASR 出最终结果时，各向同一主机发一次免费的鉴权模型列表请求，让连接池里预先有可用的热连接。修复后真实闭环中 **TTS 首帧从平均 1394ms 降到 604–638ms**，说完到收到音频从平均 3.92s 降到 3.03 / 3.56s（2 个样本）。

## 证据（系统合成固定文本，北京地域 qwen-audio-3.0-tts-flash）

`npm run voice:probe-tts -- --live` 把一次请求拆成响应头、首个音频块、首个 20ms 帧，并统计每次新建的连接数：

| 情况 | 新建连接 | 首帧（ms） |
|---|---|---|
| 进程内第 1 次 | 1 | 1780–2121 |
| 紧接第 2 次 | 1（未复用） | 1290–2022 |
| 第 3 次起，连续请求 | 0 | 478–557 |
| 11 字与 33 字句子（热连接） | 0 | 都约 0.5s，与句长无关 |
| 空闲 6 秒后 | 1 | 1435 |
| 空闲 6 秒，提前 1.4 秒做未鉴权 HEAD（返回 401） | 1 | 998–1405，连接未被复用，无效 |
| 空闲 6 秒，提前 1.4 秒做鉴权模型列表（返回 200） | 0 | 639–1121（第 1 次含进程冷启动） |
| 对照：空闲 6 秒，不预热 | 1 | 2168 |

分帧：首个 SSE 音频块固定 20160 字节（420ms 音频），收到后不到 1ms 就输出首帧，不是瓶颈。

另一个现象：进程内第 2 次请求也新建了连接。原因没查清，因为预热已绕过这个问题，所以没有继续追。

## 真实闭环（本机 LiveKit，2 次）

| 阶段（ms） | 预热前平均（4 次） | 预热后 |
|---|---|---|
| 说完 → ASR 最终结果 | 782 | 815 / 758 |
| 模型首句 | 1392 | 1201 / 1810 |
| **TTS 请求 → 首帧** | **1394** | **638 / 604** |
| 说完 → 浏览器收到音频 | 3924 | 3027 / 3555 |
| 打断（开口 → 静音，过预热期后） | 715 | 746 / 662 |

LLM 也走同一主机，说话开始时的预热本意是让模型请求也用上热连接，但 2 个样本里模型首句没有稳定改善，它受模型自身波动影响更大。不能据此宣称 LLM 变快。

## 改动

- `server/providerWarmup.mjs`（新增）：向 `QWEN_BASE_URL/models` 发一次鉴权 GET 并读完响应体（不读完连接不会回到池中）；同时最多一个在途请求，3 秒超时，任何失败都只返回 false。不发送孩子的文字或音频。`VOICE_LAB_WARM_CONNECTIONS=false` 可关闭。
- `voice-agent/agent.mjs`：ASR 报告开始说话、得到最终转写时各预热一次。第二次是因为 TTS 首次请求时，模型请求还占着自己的连接。合成模式不预热。
- `scripts/probe-tts-first-frame.mjs`（新增，`npm run voice:probe-tts -- --live`）：TTS 分段与连接复用探测。
- `tests/provider-warmup.test.mjs`（新增，3 项），已纳入 `check:voice-lab`。

验证：`npm run check` 退出 0（417 项 Node 测试加 smoke）；免费合成 WebRTC 闭环 5 组通过；真实闭环 2 次全部通过，转写完整。

## 限制

- 每轮多 2 次模型列表请求。按目前所知不计费，但会占用接口频率额度，未查供应商限流规则。
- 孩子一句话说得超过约 3 秒时，说话开始时的预热连接可能在模型请求前就过期，但转写时的那次仍然有效。
- 只在本机网络验证。到正式部署（境内服务器，离供应商更近）时，握手成本会小很多，收益也会相应变小，需要重新测。
- 更彻底的做法是给 fetch 配置更长 keep-alive 的连接池，需要引入 `undici` 依赖，并确认服务端允许的空闲时长；本次没有做。
