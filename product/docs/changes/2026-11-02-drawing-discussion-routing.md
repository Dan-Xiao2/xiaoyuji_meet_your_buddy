# 绘画话题不再误入绘图请求

## 问题与原因

“她笑我画得丑”“我今天画了一只小兔”原本会被本地白板规划器接收，返回“这一步我还没弄清楚。你能换个说法吗？”并标为needsPlanner，正常对话模型被提前绕过。原因是创作、编辑、讲述经历共用宽泛的“含画字”判断；原有少量排除词不能覆盖不同说法。

页面已有画面时，还会请求开放绘图路由。只改本地规划器不够：模型关闭或未配置时，这个路由原先也会给绘图澄清回复，不能让普通分享继续聊天。

## 修改

- `src/whiteboard/illustrationPlan.js` 增加共用判断 `isDrawingDiscussion`：含绘画词但没有明确绘图、编辑或画布控制请求时，作为对话话题。本地规划器在细节、保护对象与对象匹配前退出，避免叙述被当作修改画面的命令。
- 按句检查明确请求，去掉礼貌/意愿前缀后匹配绘制或编辑动作。“她笑我画得丑，帮我画一只猫”仍保留后半句的绘图请求。该判断不删改用户原话。
- `server/openDrawing.mjs` 使用同一判断，在既有安全检查之后直接返回chat，不需要调用绘图模型，即使模型关闭或没有密钥也适用。既有安全检查顺序不变。
- 没有“画”字的上下文编辑、颜色选择、待定对象选择继续走原路径；“清空画纸”等明确控制保留。没有改变画布数据格式、绘图能力、模型配置或API合同。

这是一项现有模块内部的路由修正，不新增服务、存储或核心组件，当前架构图关系不变。规则仍是有限语法覆盖，不能当作任意中文意图都能准确识别的证明；正常对话是否回应得好须另测。

## 验证

- 新增3组测试，改前2组失败，覆盖空白画布/已有精确画面、已有图片、分享与转述、明确绘图、混合句、颜色和编辑；对话话题保留原画，开放绘图路由不调用供应商。
- 第一版更严格的判断曾误挡“清空画纸”，既有白板测试发现后已补回明确控制支持。
- 修改现有三入口测试，用原始失败句“她笑我画得丑”替换此前绕开问题的句子，确认完整Tutor、快速及流式快速生成都能到达模拟供应商，并收到回应边界。
