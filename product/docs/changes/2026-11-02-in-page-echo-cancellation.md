# 页面内回声消除：恢复开口打断

日期：2026-11-02。

## 问题

iPhone 试用（202611021200、1212、1218 三次导出）里，开口打断出现两种失败：
- 开启系统回声消除时，iPhone 会切换成通话音频，小宇的声音发闷，并且有电流声。
- 关闭系统回声消除后，小宇自己的声音会漏进麦克风。漏进来的音量（约 0.004–0.006 RMS）和孩子的声音（约 0.006–0.01）几乎一样大，单看音量分不清：要么打断不了，要么小宇话没说完就把自己打断了。

## 第一步：先停用（已完成）

流式播放时不再监听开口打断，点按仍可打断，被点按打断的回答在下一轮请求里标记为 `interrupted`。

## 第二步：页面内回声消除

新增 `src/services/echoCancellerWorklet.js`（AudioWorklet）：
- **两路输入**：一路是不经系统处理的麦克风，另一路是小宇正在播放的声音（页面输出总线）。两路在同一个 AudioContext 里，用同一个时钟。
- **处理流程**：
  1. 降采样到 8 kHz，每 16 ms 处理一块。
  2. 用 2 ms 能量包络的互相关估计扬声器到麦克风的延迟。
  3. 延迟之后，用分块频域自适应滤波（MDF，与 Speex 同类）建模 192 ms 的回声路径，并把它从麦克风中减掉。
  4. 采用前景/背景双滤波器：孩子说话时背景滤波器会被带偏，但真正用来消除回声的前景滤波器不受影响。
- **只输出音量**：worklet 只往外报告音量（剩余、原始、播放）和延迟，不输出音频。
- **跨回答保留**：一次回答结束时保存学到的滤波器，下一次回答直接从它开始。

检测器（`bargeIn.js`）增加 `retrackMs`：
- 消除器收敛的过程中，漏进来的回声会越来越小，所以检测器每 1 秒重新估计一次"回声占播放音量的比例"（coupling）。
- 这个比例只往下调，孩子说话不会把它抬高。
- 流式播放路径的参数：`absolute 0.004, gapMs 150, ratio 2, couplingPercentile 0.9, retrackMs 1000`。

开口打断开关的文字恢复为"小宇说话时可以开口打断"。浏览器不支持 AudioWorklet 时，流式路径仍然只能点按打断。试用记录新增 `echoReduction`（dB）和 `echoDelayMs`。

## 开发过程中排掉的问题

- 最初用时域 NLMS，在语音上收敛太慢：即使是纯延迟，10 秒后也只有约 12 dB。改用 MDF 后，纯延迟约 60 dB，带混响约 25 dB。
- 有房间混响时，延迟估计会在 ±20 ms 内来回跳。每跳一次，滤波器学到的东西就丢掉大半，所以加了迟滞：只有直达声落到滤波器范围之外，或偏离超过 32 ms 时才移动。
- 第一版保存滤波器时没有同时保存偏移，下一次回答从错位的滤波器开始。已修正。
- 曾尝试把检测器的参考从"播放音量"换成"消除器预测的回声"，没有改善，已撤回。

## 模拟验证

**模拟条件**：
- 声音：用 macOS 自带中文语音（Flo 当小宇、Meijia 当孩子）。
- 房间：延迟 20、60、100、150 ms，混响 0.2–0.5 s。
- 漏音：0.4–0.8 %。
- 底噪：0.0008。
- 扬声器失真：两档。轻度为 tanh(x)；重度为 tanh(2.5x)/2.5，峰值压缩约 40%，接近削顶。
- 孩子：音量 0.005 / 0.008，分别在第 2.5、5、9 秒开口，以及全程不开口。
- 回答：第一次回答，以及沿用已学滤波器的下一次回答。

每种失真各 112 次：

| | 误打断（小宇自己打断自己） | 漏掉孩子 | 检测时延（中位 / 最大） |
|---|---|---|---|
| 原始麦克风（试点参数） | 56–60 | 0 | 0.33–0.5 s / 1.46 s |
| 回声消除，轻度失真 | 0 | 0 | 0.32 s / 1.18 s |
| 回声消除，重度失真 | 5 | 0 | 0.32 s / 0.88 s |

- **消除量**：有底噪时约 19 dB，这是底噪本身决定的上限；轻度失真约 15–18 dB，重度失真约 11–16 dB。
- **CPU**：在 Mac 上约占 1%。

**已知限制**：在页面加载后的第一次回答里，前约 3 秒消除器还在学习房间，较小声的孩子在这段时间可能打断不了。从第二次回答起，所有房间、所有开口时刻都在约 0.35 s 内识别到，并且没有误打断。

## 测试

- `tests/echo-canceller.test.mjs`，新增，用合成语音：
  - 三种房间在 4–10 秒的消除量都超过 10 dB，延迟估计误差不超过 40 ms。
  - 孩子的声音穿过消除器后，音量变化小于 3 dB。
  - 下一次回答从已学滤波器开始，第一秒的消除量超过 8 dB。
  - 按页面参数，四种房间里只有回声时都不触发；孩子开口能在 0.6 s 内识别（第一次回答在第 5 秒开口，下一次回答在第 0.8 秒开口）。
- `tests/barge-in.test.mjs`：新增 retrack 测试，确认 coupling 跟着往下调，不会被抬高。
- `tests/barge-in-browser.mjs`：在真实 Chromium 中检查：
  - worklet 能加载；
  - 安静时不会打断，说话时会打断；
  - 麦克风不开系统回声消除；
  - 试用记录里有 `echoDelayMs`；
  - 关掉开关后只能点按打断，被打断的回答带上标记。
- `npm run check` 全部通过。

## 未验证

- 还没在 iPhone 上试。真机的扬声器失真、系统音量处理和延迟都可能与模拟不同。请看导出里 `barge-in-watch` 记录的 `echoReduction`、`echoDelayMs`、`bestMargin`。
- 模拟里的孩子是成人语音调快、调高后的替代，不是真实儿童录音。

## 真机结果（202611021302）与回答变慢

**页面版本**：第 1–13 轮手机还在用旧页面，没有回声消除；第 14 轮起才是新版本。

**回声消除**：在手机上找到的延迟是 86–98 ms，每次都很接近。剩余的回声从约 2.3% 降到 0.3–0.4%，`echoReduction` 最高 8 dB。有 3 次打断时孩子的声音高出判断线 2.7–3.7 倍，应该是真的开口；另外 2 次小宇完整说完，没有误打断。小宇说话时没有电流声。

**回答变慢的原因**：孩子说完到小宇开口，中位数从昨晚的 2.2 s 变成 4.1 s。主要变化在识别出文字这一步：
- 昨晚不管说多长，约 0.4 s 出文字；
- 今天要 0.6–4.6 s，说得越长越慢。

这和回声消除无关：12:00 那段还没有回声消除，就已经这样慢了。从 Mac 直接测识别服务，提交整段音频后要 0.7–2.1 s 才确认收到，说明是识别服务今天变慢了。

**尝试过、没有上线**：让识别服务自己判断停顿（server_vad），一边听一边分段识别。实测 12 次：
- 出字时间在 0.2–5 s 之间，波动很大；
- 有 1 次识别失败、1 次超时；
- 分段太短，识别质量变差（"它的壳是黄色"→"他的可是皇"），结尾常被丢掉。

所以已撤回，继续用说完后一次提交整段的方式。

**模型同样是服务那边变慢**：从识别出文字到小宇说出第一句，真机中位数从昨晚的 1.1 s 变成 1.66 s。但这不是我们的提示词造成的：
- 昨晚测试时提示词已经是约 4660 字，现在约 4700 字；精简到最短的提示词，出第一句的时间也一样。
- 用同一测速工具，qwen3.8-max 出第一个字的时间：昨晚 21:56 约 0.76 s，今天 11:11 约 1.2–1.6 s，18:17 回到约 0.79 s。

**18:18 复测**：识别服务说完后约 0.37–0.46 s 出文字，和说话长短无关，已经恢复到昨晚的水平。

结论：中午测试时，识别和模型两个服务都比平时慢，代码不需要改。以后再遇到变慢，可以先跑 `npm run voice:probe-llm -- --live` 和实时识别的测速工具，判断是不是服务本身的问题。
