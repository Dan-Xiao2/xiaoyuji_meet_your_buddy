# 正式页面：开口打断与口语化回答

日期：2026-11-02。来源：首次 iPhone 试用后的反馈，“开口说话打断不了”“用词像念课本”（声音本身没问题）。

## 一、口语化回答

**原因：** 4–5 岁年龄规则写着“可以用简单的‘因为、所以’”，短回答提示里又没有任何口语风格要求。改前抽样中，8 个“为什么”回答里有 6 个是“因为……。……。所以……。”三段式。

**改动：**
- `src/content/ageAdaptation.js`（4–5 岁）：改为“讲一个原因时配一个孩子看得见的例子，不套用‘因为……所以……’的句式”。
- `server/qwenTutor.mjs`：短回答提示新增一条口语风格要求：像坐在孩子身边随口聊天；先用孩子自己的词接住他说的话；不用“因为……所以……”框住整段回答；不要每轮都用同样的开头或结尾；语气词不要堆叠。第一版改完后，有几个回答为了口语化丢掉了真正的原因，所以又补了一句：“口语化不等于换掉原因，为什么问题仍要先把真正的原因说对，再配一个看得见的例子。”

**抽样**（同样 5 个问题，4–5 岁，`qwen3.7-flash`）：
- 改前（8 个“为什么”回答）：3–4 个是完整的“因为……所以……”三段式。
- 改后（两轮共 16 个“为什么”回答）：完整三段式约 1 个，以“因为”开头的约三分之一。多了“就像你牵着好朋友的手一起走，不会走丢一样”“就像你跑的时候，旁边的树好像也在往后退”这类口语比喻。
- **准确性和改前差不多，两边都有错**：改前有“蓝色比较轻”“蚂蚁一起走更安全”，改后有“蓝光跑得快”“月亮像影子一样跟着你”。根源是模型没拿到相关的科学事实（例如“天空为什么是蓝色”选中的知识卡都与光无关），需要单独修知识卡选择，不在本次范围。

## 二、开口打断（barge-in）

**原先：** 正式页面是半双工的，小宇说话时麦克风关闭，只能点按语音按钮打断。

**做法：**
- `src/services/bargeIn.js`：
  - 检测器：播放开头的 500ms 用来测量回声残留（漏进麦克风的小宇自己的声音）作为基准；之后只有响度达到 `max(0.035, 残留 × 1.6)`、并且持续 300ms 的声音才算孩子在说话。音节之间 80ms 以内的停顿可以容忍。每次播放只触发一次。
  - 监听器：同步返回控制句柄，在后台打开麦克风，所以播放在麦克风打开之前就结束时，也能及时停掉。触发后把**已经打开的麦克风流交给接下来的收听**，省掉重新开麦的时间。
- `src/services/voiceService.js`：新增 `watchForBargeIn`，以及交接用的麦克风流。录音收听优先复用交接过来的流；2 秒内没有被用到就释放。
- `src/features/voice/voiceSession.js`：
  - 回答开始播放时启动监听（告别语除外）。任何停止播放的途径，包括播完、暂停、新的输入、结束会话，都会关闭监听。
  - 触发后记录 `barge-in`（从开始播放到打断的时间），然后转入收听。
  - 如果打断后的这次收听什么也没识别到，记录 `barge-in-empty`，作为误打断的近似计数。
- 家长区“麦克风”里新增开关“小宇说话时可以开口打断”，默认打开，保存在本机；“清空本机数据”时一并清除。关闭后播放期间不会打开麦克风。

**测试：**
- `tests/barge-in.test.mjs`（7 项）：
  - 检测器：忽略预热期测到的回声；持续说话时触发一次；容忍音节间隙；不因短促声音或被真正停顿打断的声音触发。
  - 监听器：触发时交出麦克风流；停止时释放；麦克风打开前就被停止时，迟到的流会被释放。
  - 会话：开口后播放停止并转入收听、记录打断时间；打断后没听到内容时记为误打断；开关关闭、告别语、暂停、播完这几种情况下的监听行为都正确。
- `tests/barge-in-browser.mjs`（已加入关键浏览器检查集）：在真实页面里，先点语音按钮、伪造语音识别说出问题，等流式播放开始后，往伪造的麦克风里注入声音。验证播放停止、转入收听、打断被记录；关闭开关后，同样的声音不会打断，也不会打开麦克风。
- `npm run check` 退出 0（438 项 Node 测试加 smoke）；`npm run check:browser` 退出 0（15 组全部通过）。

## 未验证与风险

- **没有在 iPhone 上验证。** 浏览器测试里的麦克风是合成音，没有真实回声。真机上需要重点看：
  - **外放时会不会被自己的声音误打断**：看测试数据里 `barge-in-empty` 的次数，还有你实际听到的情况。
  - **播放期间打开麦克风，iOS 会不会把外放音量调低或换到听筒**：iOS 在“录音+播放”模式下有这种行为。
  - 孩子开口后，开头的几个字有没有丢。
- 打断后复用麦克风流这一步，只在使用录音收听时才会发生（真机的云端识别路径）。浏览器测试走的是浏览器自带的语音识别，没有覆盖到；单元测试只覆盖了监听器交出流的那一步。
- 检测阈值（0.035、1.6 倍、300ms）是没有经过真机校准的初始值。

## 三、第二次真机试用后的修正（2026-11-02）

**真机数据**（iPhone，iOS 18.7 / Safari，19 轮）：开口打断 3 次，`barge-in-empty` 为 0（没有误打断，与试用者的感受一致）。说完到小宇开口中位数 2.1 秒，没有失败或回退。试用者反馈：
- 没有被自己的声音打断；
- 外放“有点像从听筒出来”：iOS 在页面开着麦克风时会切到通话音频模式。这是开口打断的代价，本次未处理；
- 措辞好一些了；
- 以及下面三个问题。

### 1. 否定之后还在说被否定的东西（“没有软软的沙子”）

**复现**（构造同样的对话，`qwen3.7-flash`）：改前 6/6 次都把“没有软软的沙子”理解成“沙子是硬的”，并继续围绕沙子展开（“硌脚”“运走硬石头”），有没有打断都一样。

**改动：**
- 短回答提示新增 `followChildInstruction`：孩子否定或纠正时以孩子这句为准，当作“那里没有／不是这样”，**不要猜成它的反面**，也不再追问被否定的东西；简短接住后，问一句或听孩子说实际看到了什么；被孩子打断的话不要接着讲完。
- **被打断的回答在历史里加注释**：语音会话发生打断时通过 `onBargeIn` 通知页面是哪条回答。页面在下一轮请求的历史里给这条加上 `interrupted: true`（只改下一轮请求，不改当前轮的目标回答，以免干扰进行中的提交校验）。`createTutorContext` 只给小宇的回答保留这个标记；服务端拼历史时显示为“小宇（说到一半被孩子打断，孩子可能没听完）: …”。

**改后**（8 次）：6 次能正确接住，例如“原来没有呀，那公园的地面是……”“你说得对，那里没有软软的沙子，那你去公园看到了什么”；2 次仍在谈沙子的软硬。有改善，但没有根除，这是模型理解能力的上限。

### 2. 同音字（牛肝菌 / 牛杆菌）

**判断：** 在构造的对话里，改前代码 3/3 次都没有沿用错字，模型本身没问题，更可能是**识别把字听成了同音字**。

**改动：**
- 实时识别带上对话上下文：浏览器建立识别连接后，先发一条 `{ type: "context", text }`，服务端把它写进 `input_audio_transcription.corpus.text`（阿里云文档列出的上下文偏置字段，上限 10,000 token；本次截取 2,000 字以内）。上下文内容由 `src/features/voice/recognitionCorpus.js` 生成：固定包含“小宇”，加上最近 6 条孩子和小宇说过的话（不超过 500 字，保留最新的部分），并像发给模型的历史一样过滤掉受保护的敏感内容。这些文字发往的就是本来就在接收这段语音的识别服务，不放进网址。
- 服务端只接受一次、并且必须在音频之前发来的上下文；重复发送会被拒绝。
- 提示里也说明了：孩子的话来自语音转写，可能有同音错字，要结合上下文理解，沿用前文已经出现的正确说法，不要纠正孩子的发音。

**真实识别对照**（系统合成语音，`qwen3-asr-flash-realtime`，北京地域）：

| 合成语音 | 不带上下文 | 带上下文 |
|---|---|---|
| 小宇你好，牛肝菌能吃吗 | **小雨**你好，牛肝菌能吃吗？ | **小宇**你好，牛肝菌能吃吗？ |
| 小宇，我在树林里找到了牛肝菌 | **小雨**，我在树林里找到了牛肝菌。 | **小宇**，我在树林里找到了牛肝菌。 |

说明上下文确实生效，“小宇”也不再被认成“小雨”。合成语音发音标准，“牛肝菌”两种情况下都认对了，所以这一项对真人发音的改善还需要真机验证。

### 3. “有时候正常说话小宇听不清”

原先的测试数据只记录成功的轮次，看不出来。现在新增三类记录，并计入 `summary.failures`：
- `capture-error`：收音出错；
- `capture-idle`：等了很久，没有检测到说话；
- `capture-empty`：说完了但识别结果为空（用户在开口前主动取消，也会记成这一类）。

下次导出的数据就能看到这些情况出现的频率。
