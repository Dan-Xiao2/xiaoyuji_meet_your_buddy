# C：模型诊断、任务进度与语音展示分离

> 复核更正：旧改前对照的CSS响应类型错误，原布局失败证据无效；纠正检查及具体原因见文末。

日期：2026-10-29。实施承接 10月28日 A 的运行诊断、B 的候选隔离。C 的目标是让任务由自己的控制器持有，语音界面从当前事实派生；没有新增状态管理框架、外部模型或云服务。

## 已完成的边界

| 数据 | 当前唯一职责与所有者 | 是否保存 |
|---|---|---|
| 正式消息、家庭资料、画面、证据 | appStore 的只读业务快照；仍由既有应用入口提交 | 沿用既有存储 |
| llmStatus | modelDiagnostics 白名单：模型、用量、延迟、fallback、知识来源等诊断 | 可保存；不包含任务进度 |
| 对话阶段、awaitingReply、replyAccepted、待接收提交凭据 | conversationController；一次回合、一份当前提交凭据 | 仅页面内存 |
| 路由/规划请求 | drawingRequestTracker，继续跟随对话 AbortSignal | 仅页面内存 |
| 独立图片任务 | 既有 drawingJob，保留独立身份和基图保护 | 任务不保存；正式图片沿用既有保存 |
| 收音、处理、播报、自动续听、媒体失败及暂停提示 | voiceSession | 仅页面内存 |
| ready/listening/thinking/speaking/retry | deriveVoiceUiState 的计算结果；app 统一渲染 | 不保存、不另建可写展示状态 |

保留 `llmStatus` 字段名及 HTTP 兼容格式，避免顺手改动服务端合同；客户端在 store 规范化和普通对话合并时移除 `pending`、`enrichmentPending`、`stage`、`message`。模型适配器的旧响应可以带这些字段，但它们不再控制任务、提交有效性、按钮或续听。该诊断对象仍是最近结果的汇总，并非逐模型调用的完整审计表。

## 提交权限为什么也要改

原来的提交判断会比较 llmStatus，其中混有阶段及等待标记。只删除字段会丢失重复提交和停止后的保护，也会让无关诊断更新拒绝有效结果。

现在控制器只接受当前有效回合实际发出的那个提交对象，接收尝试消耗一次凭据。复制出来的提交、重复消费、停止后提交、旧回合提交均拒收；领域冲突拒收后也不能恢复旧状态重试同一份提交。创建新回合或停止会清除凭据；旧回合的拒收不会清掉新回合的凭据。

`applyConversationCommit` 只负责会话、原话、目标回复及领域冲突的检查和合并。它本身不承担跨调用的一次性许可；应用必须经 `conversation.accept` 后才保存、计数、播报或启动后续请求。完成提交即使没有数据变化也只能被应用接受一次。诊断元数据更新不再使合法提交失效。

A 的回合/任务/媒体代次仍有效；B 的 pending 只有孩子原话、候选不入历史、quick 插入正式回复、complete 不改已接受回答仍有效。接受仍是内存接收，不代表成功持久化或孩子已听完。

## 语音界面怎样决定

界面直接读各控制器快照，运行诊断日志仍只用于观察和测试，不成为 UI 的数据源。任务与媒体变化只通知重算；同一轮同步变化合并到一个微任务，避免结束播放/开始收音时反复写互相矛盾的提示。

- 正在采集显示“我在听”，正在播放显示“小宇在说”。后台补全和图片生成不能把这些状态改成“正在想”。
- 等待快速回复、路由/规划、转写或播放准备时显示思考并阻止重复打开麦克风。quick 接受后，补全尚在途也不阻塞播完续听。
- 收音/播放失败由媒体持有，业务重新渲染不能抹掉“再试一次”。未接受回答的任务失败同样可重试；绘图请求异常会结束等待，不留下永久思考状态。
- 停止、离页、隐藏继续走原统一取消顺序。旧媒体回调不能恢复状态；返回页面和重载均不自动续听或重发任务。
- 旧数据的候选识别仍在加载规范化之前完成，随后清掉无法恢复的进度字段，避免先丢掉旧标记再误留候选。

媒体准备阶段仍不能点按插话；播报阶段仍是点按后停止播放再收音。这是既有半双工体验，没有实现自动全双工打断。

## 验证与发现

改前语音相关基线 125/125 通过。迁移后新增运行态/展示态专项测试，并把停止、重复完成等断言移到真正的控制器接收入口；没有删除这些保护断言。浏览器阶段等待改为读运行快照，档案耐久测试只迁移两处阶段等待，保留先前的清除确认竞态修复。

第一轮完整检查未通过：探索流程的故障注入发现异步等待谓词可能被当前 Playwright 当成真值，不能证明等待到了目标阶段。修正为预先安装只读测试读取函数，再同步轮询快照；未延长超时、跳过场景或放宽取消断言。修正后故意阻塞 quick 时的回复/续听等待确实超时，并携带正确运行身份。

完整 `check:release` 第二轮退出 0：370 项 Node 测试、知识/架构/smoke，以及 11 组关键模拟浏览器流程通过。新增语音展示流程包含390/1440px下播报、收音、失败三种情况，共6个受控场景，验证补全不能覆盖媒体状态，停止和重载不能复活旧任务。随后进一步收紧纯合并函数的旧诊断字段过滤，39项定向测试，以及候选隔离、运行态界面、儿童安全三个浏览器脚本的复核通过。

过程中普通权限运行 ASR 测试的4项失败为本机监听 `EPERM`；授权使用本机测试端口后完整检查通过。所有模型请求、识别和媒体均使用模拟数据或替身，无真实家庭资料、付费模型调用。

架构 JSON/HTML 已同步：9/9 showcase 检查通过，0 errors、0 warnings；独立自动浏览器检查通过，四个桌面尺寸无溢出，并覆盖端点尺寸浅/深色截图。已实际查看1440×900浅色及2048×1320深色图像，未见遮挡或裁切。这些是架构展示验收，不是产品语音质量验收。

## 扩展检查没有全部通过

这些不在11组关键流程内，单独记录，不并入通过数：

- `voice-browser.mjs`：最初等待系统朗读成功超时。现有网页语音规则及本轮未改动的voiceService早已禁止系统音色回退；将旧断言修正为“云端音频失败必须报错，系统朗读调用为0”。修正后390/1440px均通过，包含真实Web Audio对合成静音PCM的调度检查，不代表真实麦克风或声学质量验收。
- `drawing-browser.mjs`：补上原本缺失的appReady等待，避免表单在事件绑定前直接导航；后续在“太阳为什么发光”处，期望模型答案，实际得到备用回答，仍未通过。
- `whiteboard-browser.mjs`：换题后期望旧积木画面清空，实际保留，仍未通过。
- 使用C开始前保存的src及旧脚本进行独立390px对照，未覆盖当前代码。首次对照在更早的小屏溢出等检查停止；后续仅在诊断副本中记录全部断言失败后继续，退出仍为非零。旧绘图阶段等待无法到达，诊断副本改为等第4个回合完成后读取同一节点：改前同样得到备用回答、保留scene，且Tutor请求数为0；旧脚本的绘图路由/规划模拟返回空对象。白板改前同样得到恐龙文本回答但保留积木scene，与改后的失败一致。**这两个具体观察在390px改前可复现，未在本轮修复**；不将诊断继续执行当作正式测试通过，也不据此推断全部尺寸和布局问题根因已明。后续应单独校正旧脚本的路由模拟、画面保留预期和布局等待，不扩大本轮产品行为修改。

因此本轮结论是“C的状态分离已实现，关键回归与专项验证通过；扩展绘图/白板检查仍有未决失败”，不是全仓所有脚本全部通过。失败日志及改前诊断副本保存在本次工作目录的runtime-c证据包内。

## 2026-10-29 失败原因复核与更正

上轮改前对照把所有 /src/** 响应标为 text/javascript，误把CSS也作为JavaScript返回，污染了布局检查。这是验证工具错误，不能据此认定产品已有相同布局缺陷。本次确认CSS相对C改前未变，只替换JavaScript并让CSS正常加载；390px下布局、点击、短屏断言不再失败，原绘图/白板语义断言仍失败。日志：work/runtime-c/logs/xiaoyuji-c-corrected-baseline.log。这不等于全部尺寸的布局验收。

原因与建议：

1. drawing-browser只模拟Tutor，其余API返回空对象。已有画面时先经过绘图路由，空对象落入规划分支，规划也返回空对象，最终保留本地备用回答，Tutor请求数为0。应明确模拟chat/plan/image/clarify合同，未定义业务请求立即失败；恐龙场景分别验证图片功能关闭、可用和生成失败，不沿用早期矢量对象的固定不支持文案。
2. whiteboard-browser预期换题后清空画面，但当前规则允许保留画面继续聊天，relevantBoard直接保留有效scene。应分别验证原画保留、无无关月亮、旧回放停止；如果产品要换题收起白板，需独立定义展示规则，不能直接删除正式画面来通过测试。
3. quick模拟遗漏llmStatus.used:true，控制器因此跳过后台补全；拒绝后台月亮画面的测试实际上没有执行该响应。应补齐used并断言补全请求真实执行，门控释放后再验证原画与回复未被改写。
4. saveGrowthMoment仍用当前屏幕画面推导domain/title并附boardSnapshot，普通新话题可能关联旧图。这是证据归属缺口，不能简单将快照断言改为scene。应由本轮已接受结果决定领域及附图，普通聊天保守不附旧图，真正创建或修改画面时附相应版本。

本次只复核、纠正记录并提出修法，未修改正式运行代码或正式测试断言。
