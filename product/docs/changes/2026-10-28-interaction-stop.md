# 三批协同复盘与第三批实施记录

日期：2026-10-28。范围：当前浏览器原型的主入口拆分和停止语义。前两批代码已联合复核，第三批已实施并通过本机模拟回归。不是 LiveKit 接通或 iPhone 熄屏验收。

## 结论与前两批协调程度

拆分方向合理，但前两批还不能算一套完整的交互生命周期。正常回答路径已经衔接：conversationController 提交受限结果 → app 校验接受 → 保存/播报 → voiceSession 管理播放与续听。退出路径原先只停媒体，业务仍可能把迟到结果当作新播报命令；第一批的“拒绝旧媒体回调”保护不了这个新命令。

| 复盘项 | 做得好的地方 | 不足与本次判断 |
|---|---|---|
| 第一批语音模块 | 收音、播放、分段白板和续听集中；媒体代次隔离旧回调 | 主入口减少约181行，但新增模块197行，不是总复杂度减少；页面适配与业务状态依然耦合 |
| 第二批受限提交 | pending/quick/complete/protected 共用接收边界；拒收不保存、不触发后续模型请求；并发资料保留 | 只覆盖普通对话，设置和绘图仍有独立写路径；“受限提交”不等于唯一状态源或数据库事务 |
| 两批协同 | 接收后播报、指定本轮回复、冲突拒收及失败重播已有回归 | 缺少应用退出时跨模块的统一取消；仅模块测试不够，必须测试真实页面入口 |
| 历史正确性 | 已接受回复有回合和消息身份 | 尚未接受的本地候选曾留在历史里，停止或换问后可能进入下一轮上下文 |
| 证据质量 | 有单元检查和浏览器回归 | 之前探索流程偶发超时根因仍未知；重复通过不足以证明已修复。已接受文字也不代表孩子实际听完 |

第三批采用 app 内一个停止函数和一个对话状态纯函数，没有再增加控制器层、事件总线、SDK或服务。app 仍有1558行；三次小改动达成的是职责和取消边界改善，不能宣称入口已成为纯装配层。

## 第三批实际修改

`stopInteraction` 的顺序：取消当前对话 → 取消开放绘图 → 暂停语音 → 清理麦克风试听及按压状态 → 清除等待状态；确有状态变化时才提交保存。先使业务结果失效，再停止媒体，避免迟到业务重新发起播报。

`cancelPendingConversationState` 保留孩子原话及已接受历史，只移除有本轮身份、仍在 quick 等待阶段的未发布候选；清除 pending/enrichmentPending 并标记 cancelled。重复调用保持同一个状态对象，不产生额外状态保存。未能定位身份的历史遗留消息没有做批量清洗。

| 入口 | 行为及保存边界 |
|---|---|
| 离开聊天页、页面隐藏 | 停止业务和媒体，清理等待状态并保存；不把会话自动标记结束 |
| pagehide | 同样停止与清理；测试覆盖事件处理，不代表操作系统强杀前一定能持久化 |
| 麦克风刷新/本机试听前 | 先停止聊天和绘图，再交给现有试听模块申请设备；不让两套采集竞争 |
| 白板重播 | 先停止在途交互，再使用已提交白板重播 |
| 显式结束会话 | 先停止且不单独保存旧状态，交由结束路径一起保存；明确告别仍可播放一次结束确认，不自动续听 |
| 清空/恢复档案 | 先停止且不保存旧状态，再使用替换后的状态；保留存储代次保护，避免写回被替换档案 |
| 新输入抢在旧回答前到来 | 原有 begin 使旧对话失效，额外清除旧待定候选后准备新回合；不调用全局停止，保留合法的图片与聊天并行 |

返回页面、恢复可见或 pageshow 不自动开启麦克风。用户明确点击语音入口后可以开始，旧 pending 不再阻塞。

本轮运行文件：`src/app.js`、`src/app/appEvents.js`、`src/features/conversation/conversationState.js`。新增两个停止专项测试，并接入现有 check:voice 和浏览器发布门禁。第一批 voiceSession 的生产实现本轮没有继续扩大；独立 CI 修复的 archive-durability 测试和变更说明未改动。

## 验证过程与结果

1. 改动前语音检查95项通过，但新增12个真实页面停止场景有11个失败：切页/隐藏后迟到结果写入，pagehide/麦克风入口留下等待状态，结束留下未发布候选等。恢复档案场景原本通过，不把它计作新修复。
2. 统一停止后，初始12个场景全通过。随后补充“旧回答未返回时开始新问题”，验证下一轮历史不含旧候选、旧结果不改新状态。
3. 最终 `npm run check:release` 退出0：327项 Node 测试全部通过（档案25、语音99、成长6、安全88、服务5、白板99、浏览器启动选择5），知识/架构/smoke通过，9组模拟浏览器流程通过。
4. 新增4项纯函数检查覆盖候选清理、已接受回复保留、绘图等待不误删旧回复、重复停止，以及已准备提交的拒收。新增13个浏览器场景覆盖 quick 的切页/隐藏/pagehide/结束/重播/麦克风/恢复/新输入，以及 enrichment、speech、route、plan、image 的迟到结果。
5. 浏览器故意让取消后的请求仍成功返回，同时检查请求确实收到 abort、后续模型/语音请求未启动、状态及档案未改变、收音未重启。恢复页面不会自动收音，明确点击后能开始。
6. 原有档案清空/补全竞争保护、34个绘图竞争场景、图片与背景聊天并行、四个连续探索场景均在本次完整检查通过。未放宽旧断言或修改超时。

所有家庭、音频事件和API响应均为模拟；浏览器观察是有界的，不覆盖所有网络时序。pagehide/visibility 是事件模拟，不是 iPhone 锁屏、后台保活或真实 bfcache 恢复测试。本轮没有真实模型调用、家庭数据使用、远端 CI、提交推送或部署。

## 仍不好的地方与后续优先级

- **状态所有权仍不完全清楚。** app 的可写 state、voiceUi 展示状态、绘图独立路径仍需维护一致性。暂不为进一步缩短文件而机械拆分；后续应围绕实际变更和故障逐步减少写入口。
- **“已接受”与“已听到”仍不同。** 停止时保留已接受文本，部分未播文字也可能已保存。接 LiveKit 前需明确实际播放进度/被打断前缀合同，不能拿本次取消测试代替该能力。
- **本机多记录保存仍非原子事务。** 当前代次、逐条修订和冲突保护继续有效，但没有解决同代次跨标签页原子更新或崩溃一致性。
- **探索流程偶发超时仍待定位。** 本轮完整回归通过，原失败证据及仅失败时诊断保留；不能据此宣布根因消失。
- **仍是半双工网页。** 页面隐藏按现有产品能力停止；LiveKit系统级打断、附和识别、iPhone原生后台音频、真实儿童识别/延迟与质量都尚未验收，更不等价于模型级原生full-duplex。

下一步应先固定实际播放/取消的对接合同与最小纵向实验，再接 LiveKit。避免在上述语义未确定时同时重写前端状态、后端接口和语音运行时。
