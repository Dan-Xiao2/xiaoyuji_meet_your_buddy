# 模型首句延迟：不在提示长度，在连接；改为长连接

日期：2026-11-01。前置：[延迟拆分](2026-11-01-latency-breakdown.md)中模型首句 1.2–1.8 秒，是最大的单项延迟。

## 结论

1. **缩短提示没有用。** 在热连接上，模型首句都在约 0.55 秒，与提示长度基本无关：完整提示 1891 token、压缩知识卡 1542 token、去掉知识卡 958 token、最小提示 130 token，结果相近。所以本次**没有改提示词**。
2. **慢在冷连接**：热连接首句 0.65–1.0 秒，冷连接 1.25–1.32 秒；我们自己代码在发出请求前的开销只有 1–7ms。
3. **上一版预热的一处设计反而制造了冷连接**：Agent 在 ASR 出最终结果时又预热一次，那两个预热请求占住了热连接，30ms 后 LLM 请求发出，只能新建连接。模拟对照：出结果时再预热，首句 1462 / 1078ms，期间新建 1 条连接；不再预热，首句 567 / 582ms，不新建连接。
4. **改为长连接后**，LiveKit 真实闭环 3 次：模型首句 731 / 542 / 564ms（基线平均 1392ms），**说完到收到回答音频 2661 / 2458 / 2481ms（基线平均 3924ms）**。

## 关键测量

**提示长度对照**（`npm run voice:probe-llm -- --live`，4 轮交替，每次请求前预热，热连接）：

| 变体 | 输入 token | 首句（ms，4 轮） | 平均 |
|---|---|---|---|
| 现有提示 | 1891 | 561 / 585 / 572 / 509 | 557 |
| 知识卡压缩为单行 JSON | 1542 | 579 / 642 / 677 / 590 | 622 |
| 去掉知识卡 | 958 | 542 / 539 / 577 / 521 | 545 |
| 最小提示（只有角色、年龄、长度，不可上线） | 130 | 753 / 637 / 1074 / 680 | 786 |

**服务端空闲容忍度**：把客户端连接存活时间设为 120 秒后，空闲 6 / 10 / 20 / 40 / 70 秒再请求，都复用原连接，每次约 0.2 秒。

## 方案

不再“掐时间预热”，而是让连接在两轮之间不断开：

- `server/httpKeepAlive.mjs`（新增）：用 `undici` 设置全局连接池，空闲存活时间 30 秒。选 30 秒是为了离观测到的 ≥70 秒留出余量，降低请求写到服务端刚关闭的连接上的风险。正式服务端（`server/server.mjs`）和 Agent 进程（`voice-agent/agent.mjs`）启动时各安装一次。`PROVIDER_KEEP_ALIVE=false` 可关闭。
- 预热只保留“孩子开口时并发两条”，用于首轮和长时间停顿之后的冷启动。去掉了 Agent 在最终转写时的预热，以及正式页面在 `finish` 时的预热：两者都紧挨着回答请求，会抢占回答需要的连接。`realtimeAsr` 的钩子相应改名为 `onSpeechStart`。
- 依赖：`undici` 锁定 6.29.1。最初装的是与本机 Node 内置版本一致的 6.24.1，`npm audit` 报出高危漏洞，其中一条是“自定义 Agent 时 TLS 证书校验可能被绕过”，正好和这里的用法相关，所以改用已修复的 6.29.1。现在 `npm audit` 为 0 个漏洞。

试过、未采用：说话期间每 2 秒续热一次。真实闭环里模型首句仍是 1619ms：新进程中头几次请求很慢，续热请求还没结束，回答请求恰好撞上。定时续热躲不开这种碰撞。

## 实测

**LiveKit 真实闭环**（合成中文 1.8 秒，本机）：

| 阶段（ms） | 基线平均（4 次） | 长连接（3 次） |
|---|---|---|
| 说完 → ASR 最终结果 | 782 | 756 / 769 / 775 |
| 模型首句 | 1392 | 731 / 542 / 564 |
| TTS 首帧 | 1394 | 753 / 699 / 767 |
| 说完 → 收到音频 | 3924 | 2661 / 2458 / 2481 |

**正式服务端端到端**（WebSocket 实时 ASR → 短回答 → 同时 TTS 与补全，每轮前空闲 6 秒）：短回答 954 / 1067 / 927ms（上一版平均 1079ms），TTS 首个音频 677 / 493 / 513ms（上一版平均 736ms）。

## 验证

- `npm run check` 退出 0（421 项 Node 测试加 smoke）。新增 `tests/http-keep-alive.test.mjs`；`realtime-asr` 测试改为断言 `finish` 时不触发预热。
- `npm run check:browser` 退出 0，13 组关键流程全部通过，包括此前超时的 `exploration-pipeline-browser`。说明它的失败与机器负载有关，根因仍未定位。
- 免费合成 WebRTC 闭环 5 组通过。
- 真实闭环：去掉续热方案前，有 1 次 Agent 派发失败（no servers available），属已知的偶发问题，与本改动无关。

## 限制与未做

- 只有 3 个闭环样本，都是本机网络、合成语音、同一句话，而且每次都是会话首轮（新进程）。连续多轮对话中，后续轮次应当更快，但没有测。
- 30 秒存活时间：如果服务端在某些情况下更早关闭空闲连接，复用到失效连接的请求可能失败。实测中没有出现，但没有做长时间压测。部署到境内服务器后需要重新确认服务端的空闲策略。
- 每轮开口时多 2 次模型列表请求。按目前所知不计费，但会占用接口频率额度，供应商限流规则未查。
- 顺带发现：“天空为什么是蓝色”选中的 4 张知识卡都是通用的动手探索卡，没有与光、天空相关的。属于回答质量问题，本次未处理。

## 费用
