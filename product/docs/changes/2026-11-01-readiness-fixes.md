# 语音实验：两个就绪状态漏洞的修复，及结论收紧

日期：2026-11-01。来源：外部复核独立复现了两个就绪漏洞，并指出两处结论过强。复核者的漏洞复现未改产品代码，未调用付费服务；本次修复与验证如下。

## 漏洞 1：重连后，迟到的旧就绪消息能恢复“在听”

**原因：** 重连时客户端会把 `inputReady` 置为 false，但它接受“就绪”消息时只校验会话 ID 和序号是否递增，hello 没有编号。重连前发出、重连后才到达的就绪消息照样被接受。另外，Agent 端的就绪是整个会话只记一次的（首帧送进识别器后一直为真），所以重连后它回答的“已就绪”，并不能证明重连之后音频又到达了识别器。

**修复：**
- 客户端（`src/services/livekitVoiceClient.js`）：每次 hello 带递增的 `helloId`，只接受 `helloId` 与最新一次 hello 一致、且 `inputReady: true` 的就绪消息。重连成功（Reconnected）或 Agent 重新加入（ParticipantConnected）时作废已有就绪，重新发 hello 并启动 20 秒就绪计时。
- 识别适配器（`voice-agent/qwenStt.mjs`）：新增 `onAppend`，每送进识别器一帧就回调一次（原 `onInputReady` 只在首帧时回调一次）。
- Agent（`voice-agent/agent.mjs`）：记住最新的 `helloId`，等它之后第一帧音频真正送进识别器时，才带同一编号回复 `inputReady: true`。收到 hello 时先回复 `inputReady: false`，只是告知状态。合成模式没有识别器，仍在启动后直接回复。

## 漏洞 2：旧会话超时清理完成后，把新会话改成“失败”

**原因：** 就绪超时的处理是 `stop().then(() => onState('failed'))`。`stop()` 同步递增会话代次后，还要等远端清理请求返回。这期间用户可以开始新会话，清理返回时 `onState('failed')` 没有再核对代次。`start()` 出错时的 `await stop(); onState('failed')` 有同样的问题。

**修复：** 新增 `failAfterStop()`，在调用 `stop()` 后立即记下代次，清理完成后只有代次未变才显示“失败”。两处都改用它。

## 测试

`tests/voice-lab.test.mjs` 新增和更新：
- 重连前对旧 hello 的就绪回复，在重连后（带更新的序号）到达，不能恢复“在听”，也不能发送文字；对新 hello 的回复才能恢复。
- 旧会话就绪超时后在等待远端清理，此时新会话已就绪；清理返回后新会话仍为“在听”，从未出现“失败”。
- 不回应任何 hello 的就绪消息不算就绪。
- 识别适配器对排队中的帧不回调 `onAppend`，握手后每帧都回调。

**对照：** 把客户端换回修复前的版本，重连和超时两项新测试都失败；恢复修复后全部通过（`check:voice-lab` 34 项）。

**端到端：** 免费合成 WebRTC 闭环 5 组通过；真实服务闭环 1 次通过，转写完整。`npm run check` 退出 0（420 项 Node 测试加 smoke）。真实网络下的断线重连没有在浏览器里模拟，只有单元测试覆盖。

## 收紧的结论

- [漏词根因](2026-11-01-asr-onset-root-cause.md)：撤回“握手期间丢帧导致漏词”。复核者用旧代码做的延迟握手测试表明，旧队列也能完整保留首帧。现在只保留“服务端断句起点不偏晚”和“新版本识别完整”两条，根因列为未确认。
- [延迟拆分](2026-11-01-latency-breakdown.md)：0.72 秒是过了预热期之后测的，和之前的 2.7 秒不是同一条件，不能写成“改善”。2.7 秒是否由预热期造成，未确认。首次回答期间的早期插话被丢弃，是另一种输入丢失，需要单独验证。
- [正式页面预热](2026-11-01-formal-page-warmup.md)：“LiveKit 模型首句没改善是因为只有一条热连接”改为“可能原因之一，未证实”。

## 下一步（与复核建议一致）

1. 沿用新代码的探测与计时，用旧快照和新版本做受控首词对照。
2. 单独验证首次回答期间的早期插话，保留真机回声风险。
3. 保留已有的流式回复与连接预热；这一批不再调整模型或音色。
