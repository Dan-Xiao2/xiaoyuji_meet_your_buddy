# 语音实验开头漏词：真实探测与结论

日期：2026-11-01。问题来源：[真实联调记录](2026-11-01-livekit-real-validation.md)中 WebRTC 路径把“天空为什么是蓝色的？”识别成“为什么是蓝色的？”。

## 结论

> 2026-11-01 校正：本节原写“漏词出在本地：握手期间到达的音频没有被可靠送进识别器”，表述过强，已收回。复核中有人用保留的旧代码做了延迟握手测试，旧 SDK 队列同样完整、按序保留了首帧，所以“握手期间丢帧”这个假设站不住。下面只保留有证据支持的结论。

**已确认：** 服务端断句（server_vad）起点不偏晚，不是漏词原因。新版本在本轮条件下完整识别了开头。

**未确认：** 原 WebRTC 路径漏掉“天空”的根因。更可能的候选是：旧页面在音频真正到达识别器之前就显示了“在听”，测试脚本随即开口，开头的音频没有进入识别。新版本的输入就绪门控（就绪消息 = 首帧已送进识别器）恰好消除了这种情况，但这同样只是假设，没有做因果实验。

**下一步：** 沿用新代码的探测与计时，在同一份合成样本和同一开口时机下，对旧快照和新版本做受控首词对照，再下结论。

## 本轮真实请求（系统合成中文，Tingting，1.8 秒；北京地域 qwen3-asr-flash-realtime）

| 探测 | 设置 | 结果 |
|---|---|---|
| `voice:probe-onset` | 无前置静音，开口即说 | 转写“天空为什么是蓝色的？”；服务端 audio_start_ms=0，与真实起点相差 0ms；首帧至首次 append 1055.5ms（握手期间缓存） |
| `voice:probe-onset` | 前置 1500ms 静音 | 转写完整；服务端起点 1360ms，比真实起点**早** 140ms；首帧至首次 append 1320.1ms |
| `check:voice-lab:browser -- --live` | 本机 LiveKit WebRTC 完整闭环 | 转写完整；回答切题，未再把缺失主语猜成“云”；打断与停止通过 |

完整闭环单样本耗时（与上次口径一致，均从输入开始计时，含 1.8 秒发言）：转写 3848ms、生成 5705ms、收到非零音频 6979ms、打断至静音 2700ms。与上次 2933/5467/6463/2704ms 相比**没有改善**；逐句流式回复的延迟收益在此样本中未显现，原因待用阶段计时拆分。单样本，不是分布。

## 本次改动

- `tests/livekit-live-browser.mjs`：真实闭环检查此前只要求“出现输入”，漏词也会通过。现在默认中文样本要求转写以“天空”开头；其他样本可用 `VOICE_LAB_EXPECT_START` 指定，设为空字符串则跳过。

## 费用

两次单独 ASR 会话（各约 3–5 秒音频）、一次完整闭环（ASR 持续会话、1–2 次短回答、1–2 次 TTS）。按公开单价估算低于 0.05 元；未查询实际账单。
